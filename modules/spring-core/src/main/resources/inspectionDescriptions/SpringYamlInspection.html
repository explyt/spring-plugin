Reports in configuration files:

  • unresolved configuration values
  • deprecated configuration key
  • prohibited configuration key
  • invalid values
  • keys not in Spring's canonical form

    • Example:

    
my:
  main:
    foo-source-data: sourceFooProperties        # Cannot resolve bean 'sourceFooProperties'

    Example:

    
my:
  main:
    event-listener: org.springframework.boot.config.DelegatingApplicationListener
                                                # Cannot resolve class or package 'config'
                                                # Cannot resolve class 'DelegatingApplicationListener'

    Example:

    
servertomcat:
  accesslog:
    locale: enUS                                # Unknown encoding: 'enUS'

    Deprecated configuration key.

    Example:

    
my:
  main:
    foo:
      max-connections: 7                        # Deprecated: This method is no longer acceptable, use 'my.server.max.connections'

    Code Cleanup can normalize a key when its relaxed spelling matches a name from metadata or @ConfigurationProperties. It skips indexed and map entries, keys with the same relaxed name across the file's YAML documents, and keys whose value or enclosing mapping is referenced by an alias. It also skips renames that would affect sibling keys or edit another file. Deprecated-key replacements, removals, and file creation are not part of cleanup.

    Example:

    
my:
  main:
    name: delete                                # Invalid value 'delete', must be one of [none, validate, update, create, create-drop]

    Example: (file: application-dev.properties)

    
# Property 'spring.profiles.include' cannot be set in profile specific configuration
spring:
  profiles:
    include: foo

# Property 'spring.profiles.active' cannot be set in profile specific configuration
spring:
  profiles:
    active: bar

# Property 'spring.profiles.default' cannot be set in profile specific configuration
spring:
  profiles:
    default: baz

    You should always refer to property names in the placeholder using their canonical form (kebab-case using only lowercase letters). This will allow Spring Boot to use the same logic as it does when relaxed binding @ConfigurationProperties. For example, ${demo.item-price} will pick up demo.item-price and demo.itemPrice forms from the application.properties file, as well as DEMO_ITEMPRICE from the system environment. If you used ${demo.itemPrice} instead, demo.item-price and DEMO_ITEMPRICE would not be considered.

    Example:

    
my:
  main:
    name: ${not.in.A_kebab_case}                                # Should be kebab-case
