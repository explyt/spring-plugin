Reports a @Bean method whose bean name is already declared by a differently named @Bean method of the same configuration class, including @Bean methods it inherits from its superclasses and interfaces. When both methods are inherited, the problem is reported on the name of the class that inherits them, since Spring fails while registering that class, unless both are declared by one superclass that is itself a Spring component, such as a @Configuration class, and the problem is already reported on that superclass. A superclass on which the problem is not reported, or is only a weak warning, for example a @Component with @Bean methods when bean definition overriding is allowed, does not hide a different problem of a subclass, such as a @Configuration subclass that fails on Spring 7.

Spring Boot disallows bean definition overriding by default, so on Spring Framework 6.2.0 and later such a configuration fails at startup with BeanDefinitionOverrideException. Overloaded @Bean methods with the same method name are merged by Spring and are not reported.

When the shared name is the primary bean name of both methods, that is the first name declared in @Bean, or the method name when none is declared, Spring Framework before 6.2.0 starts with such a configuration whatever spring.main.allow-bean-definition-overriding says and silently ignores one of the two methods, so the problem is reported there as a warning, for @Configuration and lite classes alike. Which method is kept cannot be told from the source order. When the Spring Framework version cannot be determined and overriding is not allowed, a collision of primary names is reported as a warning that names both outcomes.

A name declared after the first one in @Bean is an alias. Unless bean definition overriding is allowed, an alias shared by both methods fails at startup on every Spring Framework version. A name that is the primary bean name of one method and an alias of the other fails at startup from Spring Framework 6.0; before 6.0 the outcome depends on the order Spring registers the two methods: it fails at startup or silently ignores one of them, so the problem is reported there as a warning, as it is when the Spring Framework version cannot be determined. Such alias collisions fail with BeanDefinitionOverrideException or IllegalStateException.

When spring.main.allow-bean-definition-overriding=true is set in the module configuration, Spring starts but registers only one of the two methods and never calls the other, so the problem is reported as a weak warning. This holds for a collision of primary names on Spring Framework 6.2.x, for a lite class such as a @Component with @Bean methods, also on a Spring Framework version that cannot be determined, and for a @Configuration(enforceUniqueMethods = false) class, also when enforceUniqueMethods is set through a composed annotation; which method is kept is not named, since it changes between Spring Framework versions. For a name that is the primary bean name of one method and an alias of the other, from Spring Framework 6.2.7 the declaration order decides: when the method with the primary name is declared first, only the other method is called, and when it is declared second both are called and nothing is reported. The weak warning says that Spring may register only one of the two methods whenever the declaration order cannot decide it: below Spring Framework 6.2.7, whether or not the two methods are declared in the same class, when they are declared in different classes of the hierarchy, or when the Spring Framework version cannot be determined. An alias shared by both methods is not reported, since Spring calls both. For a collision of primary names Spring Framework 7 fails at startup in any other @Configuration class whatever the property says, so the problem is always an error there, and it is reported as a warning when the property allows overriding but the Spring Framework version cannot be determined.

Methods annotated with @Profile or another @Conditional annotation, such as @ConditionalOnProperty, are not reported: Spring evaluates their conditions before it registers the bean name, so only one of them may be active.

When the value of spring.main.allow-bean-definition-overriding cannot be resolved, for example because it is a placeholder or depends on a profile, an error is reported as a warning that says so, except for a collision of primary names in a @Configuration class on Spring Framework 7, which fails whatever the value is. A warning about a Spring Framework version before 6.2.0 or before 6.0, or a version that cannot be determined, is kept as it is.
